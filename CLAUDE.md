## Project: home-os

Intelligent home maintenance companion. Captures a homeowner's issues (photo + description), triages them via a two-phase AI diagnostic conversation, helps the user decide between DIY and contractor paths, and tracks the lifecycle from capture through close. Calm authority, not anxiety amplifier — spiral prevention is an explicit design goal. PWA on the dark warm-charcoal ground.

### Gotchas

Non-obvious rules surfaced by shipping work. Read before touching the relevant area. Add an entry only when a real gotcha bit a session — not preemptively.

- **PostgREST returns `data: null` + populated `error` on a non-existent column; downstream code typically swallows the error.** Any `.from(...).select(...)` that names a column that doesn't exist (typo, stale generated types, or a FK that was deliberately not added) responds with `{ data: null, error: { message: 'column "<x>" does not exist', ... } }`. The next line that touches `data.<field>` crashes with `TypeError: Cannot read properties of null (reading '<field>')` — a generic null-deref that looks like missing-data, not a column typo. **Always check `error` before consuming `data`** at every `.select()` call site (single-row AND array form). Don't rely on the `<Row>` generic — that's a compile-time cast against generated types, which can be stale post-migration.
- **`.trim()` on every `NEXT_PUBLIC_*` env read.** A trailing newline or space in a copy-pasted env value silently 500s SSR routes via Supabase URL parsing. Defense lives in `apps/web/lib/supabase/{client,server}.ts` and `apps/web/middleware.ts` already; replicate at any new env-read site.
- **`PRODUCTION_URL` lives in two places with different formats.** `.devcontainer/.env` wants the bare hostname (`<your-app>.com`) — consumed by `/usr/local/bin/refresh-allowed-ips.sh`. The GitHub Variable wants the full URL form (`https://<your-app>.com`) — consumed by `.github/workflows/keepalive.yml`. Don't paste one into the other.
- **Anthropic SDK `web_search` server-tool name drifts with SDK version — pin it empirically.** `@anthropic-ai/sdk@0.96.0` ships TWO `web_search` variants in its `ToolUnion`: `WebSearchTool20250305` (type `'web_search_20250305'`) and `WebSearchTool20260209` (type `'web_search_20260209'`). Both share `name: 'web_search'`. The triage wrapper at `apps/web/app/api/triage/_lib/anthropic.ts` exports `WEB_SEARCH_TOOL_TYPE = 'web_search_20260209' as const` — pinned to the newer variant. When bumping the SDK version, re-verify by `grep -E "WebSearchTool[0-9]+" node_modules/@anthropic-ai/sdk/resources/messages/messages.d.ts` and update the constant + this entry. Do NOT take the tool name from memory or from a doc — the SDK pinned in `package.json` is the source of truth.
- **`tool_choice: { type: 'tool', name: '…' }` forces the model to use the tool, but the model can still refuse.** Even with `tool_choice` forcing, Claude can return a `text` block expressing inability + no `tool_use` block, or a malformed `tool_use.input`. The triage route handler defensively parses `response.content` to find the `tool_use` block + validates the input at runtime via `parseInitialRead` (`apps/web/app/api/triage/_lib/parse-tool-output.ts`). On parse failure: revert state to `capturing` + return 502 `triage_invalid_output`. Type system cannot enforce model behavior — runtime validation is the LLM-response trust boundary. Same posture applies to any future Anthropic tool-use surface.
- **plpgsql OUT-parameter names from `returns table (...)` collide with table column names of the same name in the function body.** PostgreSQL's default `#variable_conflict` mode is `error`, so any bare reference to the OUT name (in `WHERE`, `RETURNING`, etc.) inside a function whose body also touches a table column with that name fails with `42702: column reference "<name>" is ambiguous`. Demonstrated in migration 007: `start_triage` + `complete_triage` declared `returns table (card_id uuid, state public.card_state)` and used `where cards.id = ... and state = '<value>'` — the bare `state` was ambiguous with `cards.state`, and every "Read this for me" click 500'd in prod. The triage E2E exercises the RPC under local Supabase, which appears to resolve the ambiguity differently (likely an older plpgsql or a non-default `#variable_conflict` setting), so the slow-job green claim from PR #19 hid the bug. Fix pattern: qualify the column reference (`cards.state`, not `state`) in WHERE / RETURNING (migration 009 demonstrates). Audit pattern when adding a `SECURITY DEFINER` RPC with a `returns table (...)` shape: grep the function body for unqualified references to any OUT-parameter name; if any are present, qualify them with the table name.
- **Supabase Cloud projects scaffolded by `/ak-new-project` do NOT ship the standard `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON TABLES TO anon, authenticated` block — so any new public-schema table is invisible to the `authenticated` role until a migration GRANTs it explicitly.** Local Supabase + Vercel preview both hit the local stack (which does ship the defaults via `supabase init`), so E2E + previews pass; prod 42501s on the first direct PostgREST SELECT. Every write surface that goes through a SECURITY DEFINER RPC (e.g. `claim_card_slot`, `start_triage`) keeps working because the function owner has the privilege, so the symptom hides until the FIRST direct table SELECT under the `authenticated` role — which in this project was `/cards/[id]` post-capture, producing a production 404. Migration 008 grants the privileges + sets the default for future tables; new feature migrations on top of that don't need to re-think privileges as long as the default-privileges block stays in place. Audit pattern: `select grantee, privilege_type from information_schema.role_table_grants where table_schema = 'public'` against prod after every new-table migration.
- **In Next.js App Router, the layout and the page's server-component data fetches run in parallel — if both can throw, the _first_ throw wins.** The (app) layout calls `supabase.auth.getUser()` and `redirect('/login')` on null; a page that ONLY relies on RLS + the layout for auth gating can throw `notFound()` faster than the layout throws `redirect()` (e.g. a fresh-after-POST navigation where the cards SELECT runs concurrently with getUser()), producing a confusing 404 instead of a /login bounce. The fix is defensive: re-call `getUser()` _in the page itself_ and `redirect()` early before any RLS-scoped query. Demonstrated at `apps/web/app/(app)/cards/[id]/page.tsx`. Apply the same pattern to any new authenticated page that runs an RLS-scoped query — relying solely on the layout's redirect is racy.
- **Vercel env-var limit is 4096 bytes per variable.** `TRIAGE_SYSTEM_PROMPT` is the only operator-tunable env in the triage surface and is bounded by `PROMPT_MAX_CHARS = 3500` in `apps/web/app/api/triage/_lib/prompt.ts` (leaving headroom for trailing whitespace / encoding overhead). The `prompt.test.ts` length assertion catches regressions before deploy. Any future operator-tunable prompt env var should follow the same `≤ 3500` posture and the same paired-test pattern.
- **Magic-link sign-in fails in Safari Private Browsing** (iOS + macOS). The `signInWithOtp` PKCE flow stores a `code_verifier` cookie when the user submits their email; the server-side `/auth/callback` route needs that cookie present at `exchangeCodeForSession(code)` to complete the handoff. Private Browsing tabs isolate cookie state across tabs — when iOS Mail opens the magic-link in a new Private tab, the verifier from the original tab is gone, and exchange fails → `/login?error=callback_failed`. **Workaround for invitees**: use a regular (non-private) browser window. Decided 2026-05-15 as "won't fix" — flipping to OTP-code flow would eliminate the failure class but the OTP code-entry UX is a larger change deferred to PRODUCT-ROADMAP. The current `/auth/callback` route at `apps/web/app/auth/callback/route.ts:80` silently swallows the exchange error (no `Sentry.captureException`, no reason passthrough to `?error=`) — that observability gap is a separate `TODOS.md` item to fix independent of the Private Browsing decision.
- **Supabase inbuilt-SMTP rate limit is ~2 magic-link emails/hour project-wide** (not per-email-address; not per-IP). On a fresh prod deploy the first 2-3 invitees burn the bucket; the next attempt sees `429` and the form shows "You're sending links too fast. Wait a minute." — but the actual reset window is up to an hour, not a minute. The copy in `apps/web/app/login/_components/LoginForm.tsx`'s 429 branch lies about this. Two fixes available: bump the rate limit at `https://supabase.com/dashboard/project/<ref>/auth/rate-limits`, or wire Resend SMTP (3k free/month) at the same dashboard's email-settings tab. Both lift the cap significantly. The copy bug is tracked in `TODOS.md`.
- **Q&A `is_location_ask` flag is set on BOTH the user reply row AND the assistant question row for a location turn.** The user row's flag is what `_lib/round-state.qaUserCount` filters on (`role='user' AND is_location_ask=false` per D4 — location asks are free questions outside the 3-round budget). The assistant row's flag is what the next-turn handler reads via `_lib/round-state.priorWasLocationAsk` to decide whether the CURRENT user answer should dual-write to `users.location` (D6). Setting both on the same turn means round-counting can filter on either side and the location-turn detection survives page refreshes — no transient client state involved. `apps/web/app/api/triage/answer/route.ts` passes `p_is_location_ask = parsed.value.is_location_ask` (the AI's declaration for the assistant row) to `answer_triage_round`; the RPC sets the same flag on both inserted rows.
- **Q&A location dual-write to `users.location`: silent location-cache miss is tolerable, not 500-worthy.** When the prior turn was a location-ask, `POST /api/triage/answer` writes the user's answer in TWO places — first the `triage_conversations` row via `answer_triage_round` (atomic), then a separate UPDATE to `public.users.location` (best-effort, user-context client + RLS). **If the UPDATE fails after the round insert succeeds**: log a Sentry warning (not exception) and STILL return 200 — the round IS saved; the silent location-cache miss is tolerable since the next location-ask round will re-ask. Rolling the round insert back just because the secondary write failed would surface a "Q&A failed" error to the user when the Q&A actually succeeded. Single-direction failure is the right trade-off; the user-visible Q&A loop must not be hostage to the side-channel write.
- **`users.location` is stored verbatim — no geocode, no normalization, no validation beyond `< 2000 char` truncation.** The user types free text (ZIP, city, neighborhood, "near downtown San Francisco"). Store the answer string verbatim in `users.location`. The Claude Q&A prompt receives `users.location` as-is per eng-review § Location handling — the AI interprets natural-language location like a smart human would. Geocoding is a v1 concern (precise-radius weather + zone-code queries); v0's posture locks the value-shape early so row #5 (`monitor-beta`) reading `users.location` doesn't trip over an unexpected JSON-vs-string split.
- **Q&A force-confirm at round 3 + skip — server-side cap, server-side parse defense.** `POST /api/triage/answer` flips `tool_choice` to `{ type: 'tool', name: 'confirm_assessment' }` when `qaUserCount >= 3` (the 3-round budget per D4) OR `body.skip === true` (the user-requested skip per D9). The model can STILL return: (a) an `ask_next_question` tool_use block (defying the force), or (b) a malformed `confirm_assessment` input. Server must still validate via `parseQaTurn`: on either failure mode, return 502 `triage_invalid_output` + Sentry capture + NO DB write. The route never trusts that `forceConfirm` guarantees a `confirm_assessment` payload — it always dispatches through `parseQaTurn` and branches on `parsed.tool`. Same posture as PR #19's `tool_choice` forcing for `record_initial_read` (CLAUDE.md § Gotchas — `tool_choice` forces but model can refuse).
- **Migration 010 `tool_name` backfill targets PR #19's initial-read rows specifically — narrow the predicate.** When the `tool_name` column was added, pre-existing assistant rows from PR #19 had `tool_name=null`; the migration's `update public.triage_conversations set tool_name = 'record_initial_read' where role = 'assistant' and tool_name is null and round = 1` backfills only those rows. Forgetting this backfill (or widening it without the `round = 1` predicate) breaks `<ConversationRow />`'s render-by-tool-name dispatcher — null-`tool_name` assistant rows hit the fallback "Unparseable conversation row" copy + leak via the user-visible thread. The CHECK widen from `round between 1 and 3` to `round between 1 and 5` ordering also matters: drop-then-add the constraint AFTER the column add + backfill so the migration is one-transaction-friendly (no enum split needed since no enum touched).
- **`card_state` rename-recreate now happens through functions that reference the old type — drop dependent functions BEFORE the rename.** Migration 011 widens `card_state` for the third time (after 006a and 010). The previous two iterations rename-recreated the enum cleanly because no functions held references to it. But by 011, three SECURITY DEFINER RPCs (`start_triage`, `complete_triage`, `confirm_triage`) declare `returns table (... public.card_state)`. The old type cannot be dropped while those return-table signatures depend on it — the rename-recreate fails with "cannot drop type public.card_state_old because other objects depend on it". Fix: `DROP FUNCTION` all three at the top of migration 011 (before `ALTER TYPE ... RENAME`), then `CREATE OR REPLACE` them at the bottom against the new (wider) enum. The 006a rename-recreate recipe assumes no function dependencies; 011 codified the extension. Same pattern applies any future time `card_state` widens — audit functions for return-table refs and drop them first. See migration 011's "Function-dependency dance" header comment for the canonical sequence.
- **Locked-jsonb-shape validation lives in TWO places (deliberate DRY-tension).** The same `DiyExpansion` + `ContractorExpansion` shapes from spec § D3 are validated at (a) LLM-output time in `apps/web/app/api/triage/_lib/parse-qa-output.ts` (the `confirm_assessment` tool's expansion fields) and (b) user-PATCH time in `apps/web/app/api/card/[id]/estimate/_lib/parse-estimate-override.ts` (the override jsonb). Both delegate to the shared module `apps/web/app/api/triage/_lib/estimate-shapes.ts` — `parseDiyExpansion` + `parseContractorExpansion`. Do NOT inline either validator at the call site; a shape drift in one path would silently let the other accept rejected shapes. The shared module is the contract; if it tightens, both trust boundaries get the update for free.
- **`<ChoosePath />` decide_path_changed fires from a snapshotted prop, not from the post-refresh DB row.** When a user is on `<PlannedView />` and re-commits to a different path, the route returns the NEW path; if `<ChoosePath />` reads "previous chosen_path" from the refreshed card row, it'd see the new path and the from→to comparison would always be `from === to`. Fix: `<PlannedView />` passes `prevChosenPath={card.chosen_path}` as a prop to `<ChoosePath />` BEFORE the commit fires; `<ChoosePath />` reads it from props (frozen at render time), fires the event, then `router.refresh()`. The next render gets a new `prevChosenPath` from the freshly-refetched card row. PostHog event firing in ChoosePath has a one-render-cycle window — the prop is the snapshot that survives the refresh.
- **`card_state='decide'` is the new "confirmed, awaiting path" state — `diagnosed + severity_confirmed=true` is the legacy synonym.** Migration 011's backfill lifts existing `diagnosed + severity_confirmed=true` rows to `state='decide'`, and `confirm_triage` now writes `state='decide'` directly. The `cards/[id]/page.tsx` body retains the `diagnosed + severity_confirmed=true` branch as a defensive fallback for any rows that escape the backfill (e.g. a row mid-flight at migration apply time, or a future direct-DB seed that bypasses the RPC). When auditing card lifecycle code, treat `decide` as the canonical "confirmed, path-not-chosen" state; `diagnosed + severity_confirmed=true` is a transitional artifact that should approach zero volume.
